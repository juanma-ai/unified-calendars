# Project rules

- Do not use a bare command-line helper's embedded `CFBundleIdentifier` with `tccutil`; because it isn't registered with LaunchServices, reset the Reminders service globally or package the helper as an app bundle first.
- For macOS TCC-protected APIs, an embedded plist in a bare executable is not a substitute for a LaunchServices-recognizable `.app` bundle; test the bundle identity and usage-description keys before testing permissions.
- For TCC-sensitive helpers launched by Electron, test with Electron as the responsible parent process; a Node/Terminal adapter test can pass while the identical direct child launch is denied under Electron.
- When renderer state depends on a main-process refresh, await the refresh before requesting derived status; parallel IPC calls can display stale status even when the underlying integration succeeds.
- For the calendar UI redesign, use `@wordpress/ui` for standard controls, menus, popovers, dialogs, notices, and color selection wherever an equivalent exists; create custom components only for calendar-specific layout and event rendering.
- The calendar sidebar must keep its search field fixed while the calendar list scrolls independently, and the weekly calendar must use an hourly time grid with a separate all-day row.
- The sidebar source-status footer shows only failing sources; when every source is ok it renders nothing. Full per-source status lives in Settings, not the sidebar.
- Keep account connections and persistent source configuration in a dedicated Settings screen; reserve the calendar sidebar for quick visibility filtering, colors, search, and hidden-event access.
- Calendar selection is two-level: Settings decides which of the account's calendars (e.g. the many calendars available in a Google account) are listed in the sidebar at all, and the sidebar then offers a quick hide/show toggle per listed calendar to control its events in the grid. Neither level replaces the other.
- The app must expose a clearly labeled text Settings action in the global top bar and must not rely on clipped footer text or icon-only controls for critical account-connection guidance.
- Week navigation, the week range label, the Settings link, and Refresh now live in a single global top bar above the sidebar and grid; do not float those controls over the calendar.
- The whole sidebar calendar row is the quick hide/show toggle (`aria-pressed`, filled swatch when visible and outlined swatch when hidden); the three-dots menu holds the color picker plus, only for sources with a web destination (Google, Trello), a source-labelled open-in-provider item built by `getCalendarLink` (`src/renderer/src/calendarLinks.js`) — sources without one (Reminders, Time Tracker) render no item at all, never a disabled one. The row itself already does hide/show.
- Hidden events are reviewed inline in Settings -> Hidden events, never in a modal; the sidebar link navigates to that tab.
- Event colors are stored as-is but rendered through `getEventPalette` (`src/renderer/src/eventColors.js`): a soft tint with dark text for light colors and a solid fill with white text for dark ones. It runs after the Trello unassigned lightening, so both distinctions survive. Do not hardcode `color: #fff` on event pills.
- Quick hide/show actions in the calendar sidebar must never remove a calendar from the sidebar; hidden calendars selected in Settings must remain listed with muted text.
- Calendar sidebar row overflow actions must use the standard three-dots menu affordance without custom square-button styling.
- Calendar sidebar row overflow menus must reveal the three-dots trigger on row hover or focus, but only open the options menu after trigger click or keyboard activation.
- Calendar sidebar row overflow triggers must match Gutenberg List View's options button pattern: `moreVertical` icon, `Options` label, small button size, and `block-editor-list-view-block__menu` on the toggle button.
- Trello cards not assigned to the current user should be visually de-emphasized enough to be obvious at calendar-grid density; a 30% lighter background is too subtle, so use a stronger distinction such as 60% lightening.
- Menu-bar/tray agenda features must expose a visible macOS status-bar title, not only a tiny icon or tooltip, so `npm start` and packaged builds are easy to discover.
- An event belongs to *every* day it covers, not only the one it starts on, and `getEventDayRange` (`src/renderer/src/calendarViews.js`) is the single place that decides which days those are. Both ends are off-by-one traps it already handles: an all-day `end` is exclusive (Google sends a one-day event on the 20th as `end: 2026-08-21`), a timed event ending on the stroke of midnight does not reach the next day, and a date-only boundary is a floating calendar date that must be built from its digits — parsing `2026-08-20` as an instant puts it at UTC midnight, which reads as the 19th in any western zone. Never re-derive this with `isSameDay(event.start, day)`; that filter is what used to hide a four-day conference on three of its four days.
- Multi-day events are drawn as one bar spanning their columns, in the month grid and in the week's all-day row alike, both packed by `buildDaySegments`. A bar cut by the edge of a week carries `continuesBefore`/`continuesAfter`, which square off that end and add a chevron, so it reads as continuing rather than as two separate events. `EventPill` also hides the start time on a continuation day and puts the full span in its accessible name. `Dropdown` wraps the pill in an inline-block div, so a segment needs `> .components-dropdown { display: block }` or the bar shrink-wraps to its title in the first column it covers.
- `getResizeResult` measures the dragged edge from the event's own start day and caps it at that day's midnight, so it cannot express an event running past one. Any block clipped at either end (`continuesBefore`/`continuesAfter`) must not offer a resize handle, by pointer or by keyboard.
- All per-view date maths (fetch range, grid days, range label, prev/next stepping, event bucketing) lives in `src/renderer/src/calendarViews.js` and is covered by `test/calendar-views.test.mjs`; view components render, they do not compute dates. The renderer keeps one `anchorDate` plus one `calendarView`, and every fetch range comes from a single `getViewRange` call so navigation and Refresh now cannot drift apart.
- Any Google `events.list` call must follow `nextPageToken`; the default page caps at 250 events, which a week never reaches but a month or year does, silently truncating the tail of the range.
- The source cache in `src/main/aggregator.js` is keyed by source *and* range (`src/main/sourceRangeCache.js`). Keying on source alone makes every view switch evict the previous view's entry and refetch all sources.
- When a menu-bar/tray agenda is expected to follow native Mac menu behavior, use Electron's native `Menu`/`MenuItem` instead of a custom floating `BrowserWindow` popover unless custom rendering is explicitly more important than native dismissal, typography, spacing, and menu interaction.
- Google Calendar write access is a separate OAuth grant: accounts connected before the `calendar.events` scope existed stay read-only until reconnected, so gate editing on the per-account `canEdit` flag rather than assuming a connected account can be edited.
- Trello cards and Reminders are points in time, not intervals; they can be moved but never resized, and `eventMutations.js` rejects a duration change for those sources.
- Agenda is a rolling `AGENDA_DAYS`-long list starting on the anchor day, not a month grid: it opens on today, steps by whole windows, and labels itself as a date range. Do not fold it back into `monthGridRange` — starting on the month's first grid cell puts stale days above today.
- Event notifications are fed by the menu bar agenda's rolling today range (`onEventsRefreshed`), never by the calendar grid's fetch; the displayed view must not decide what gets notified. `createEventNotificationScheduler` also refuses to arm anything past its horizon, because `setTimeout` overflows its signed 32-bit delay past ~24.8 days and fires immediately — a year-wide range once dumped every distant event as an instant notification.
- Never re-parse composite event ids (`google:<account>:<calendar>:<event>`) to address a provider; use the `providerCalendarId`/`providerEventId` fields the mappers emit.
- Both agenda surfaces — the menu bar dropdown (`buildAgenda`) and the in-app Agenda view (`buildAgendaSections`) — are forward-looking and exclude `timetracker` events, which record work already done. A per-project *summary* of today's tracked time is welcome in the menu bar; individual sessions as agenda rows are not. A running session also maps to `end = now`, so letting it through would make it eligible as `nextEvent` and put a project name in the tray title instead of the next meeting.
- `resolveDataDir()` in `src/main/sources/timetracker.js` is the only place a tracker path is built: stored preference (Settings → Change folder) → `TIMETRACKER_DIR` → `~/.timetracker`. The setting only tells the calendar where to *read*; the tracker keeps writing to its own directory, so any UI exposing it must say so or the two silently diverge.
- The time tracker source is no longer read-only: the calendar owns starting, stopping and noting, and the SwiftBar plugin it replaces is being retired. Writes go through `/usr/bin/sqlite3` without `-readonly` and every interpolated string passes through `quote()` in `timetrackerWriter.js`, because the CLI has no bind parameters. Contention uses the `.timeout` dot-command, never `PRAGMA busy_timeout` — the pragma returns a row, so under `-json` it prepends its own array and the real result stops parsing. `canEditEvent` still returns false for `timetracker`: nothing here edits events by dragging.
- Notes are mirrored to `~/.timetracker/notes/<project>.md` in the exact format the SwiftBar plugin used, because the calendar appends to files that plugin already wrote and a different heading or bullet shape would leave a visible seam mid-file. Notes no longer arrive in chronological order — a note can be added to a session that ended days ago — so `placeNote` slots a backdated bullet into its own `## YYYY-MM-DD` section, in time order, and falls back to a plain append whenever the note belongs to the newest day. Editing and deleting a note touch the database only: the mirror is a log of what was typed, the database is what the calendar reads, and rewriting a bullet in place is exactly the seam this format exists to avoid.
- A source may report `ok: true` with `detected: false` when it has nothing behind it but that is not a failure worth surfacing (the time tracker with no database). The sidebar footer stays quiet for those, but Settings must not render them as "Connected".
- `styles.css` fails silently: a merge that eats a rule's `}` and the following section banner's `/*` produces no error — the parser just swallows the next rule whole, and the sidebar's Time Tracker report rendered unstyled through two merges before anyone noticed. `test/styles-css.test.mjs` checks comment openers and brace balance for exactly this; run it after any merge that touches the stylesheet.
- The calendar grid carries no legend. The scheduled pill and the tracked lane bar are told apart by shape, and a bar names itself on click, so a permanent strip above the grid was only spending vertical space (`SourceLegend` and `shouldShowSourceLegend` were deleted for this reason). The tracker's db path belongs in Settings, not over the calendar. Do not reintroduce a legend.
- A tracked lane bar in the day/week grid is clickable and opens `TrackedSessionPopover`, the same card `EventPill` opens for a tracked event elsewhere. That popover is the only place session notes surface in the calendar; a bar must never be an inert `role="img"` div again, since that leaves the notes unreachable from the surface tracked sessions are most visible on.
- Transient feedback for a reversible action (completing a reminder) is a `Snackbar` in `.calendar-snackbars`, never a `Notice`: a full-width notice above the grid reflows the whole calendar down for something that undoes itself in ten seconds. `Notice` stays for errors, which should be sticky and demand attention. The snackbar is offset past the 320px sidebar so it never covers the source-status footer.
- `TrackedSessionPopover` is no longer read-only and must not claim to be: "edit in Time Tracker" named a plugin that is being retired, so the card itself is where a session's notes are added, corrected and removed. A note is addressed by `notes.id` — never by `ts`, which two notes can share and which the card rounds to the minute — and an edit writes back `rawText`, not the parsed text, or the `todo:` marker is stripped off every note it touches. Notes without an id come from a database read before the column was selected; those render but offer no editing.
